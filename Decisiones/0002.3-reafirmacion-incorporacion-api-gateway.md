# 0002.3 - Ratificación de la incorporación del API Gateway

- **Estado:** Aceptada.
- **Fecha:** 2026-11-10
- **Decisores (ASS):** Antonio Machuca y Enrique Aldama.
- **Consultados (ASC):** Sergio González y Sara Guillen.
- **Informados (ASJ):** David Sticea y Elena Romera.


## Contexto Y Planteamiento del Problema

Los arquitectos senior propusieron incorporar un API Gateway para distinguir si los lectores del periódico digital acceden desde un PC o una Tablet.

Durante la revisión de los arquitectos cognitivos se cuestionó si realmente era necesario incorporar este componente o si suponía añadir demasiada complejidad a la arquitectura sin ser necesario.

Al final, los senior decidieron mantener el API Gateway, siguiendo la orientación del profesor Rafael Capilla y teniendo en cuenta las observaciones realizadas durante la discusión y limitando sus funciones para evitar introducir responsabilidades innecesarias.

Por tanto, esta decisión recoge el resultado de la revisión y confirma la solución elegida inicialmente.

## Requisitos Motivadores (Decision Drivers)

- **Requisito clave:** RF1 - Discriminación del cliente (El sistema debe distinguir si el cliente es un PC o una Tablet). En esta reafirmación no se introduce ningún requisito nuevo

Además, se mantiene la comunicación mediante HTTP/REST establecida en el RD2, que ya se había tratado en la ADR-0001.3.

## Opciones Consideradas

Las tres alternativas que se analizaron en la decisión:

- **Opción 1:** API Gateway como punto de entrada encargado de identificar los dispositivos y redirigir las peticiones al backend.
- **Opción 2:** Middleware común en el backend para identificar el dispositivo antes de que la petición llegue a los controladores REST.
- **Opción 3:** Identificación desde el frontend mediante CSS y JavaScript, sin incorporar un componente intermedio.

## Decisión Adoptada

Se mantiene la **Opción 1: Incorporación de un API Gateway** para resolver la discriminación de clientes PC y Tablet.

Tras el cuestionamiento de los arquitectos cognitivos, los senior consideran que esta solución permite separar la identificación de dispositivos de los controladores del backend.

Para evitar complicar innecesariamente la arquitectura, se confirma que el API Gateway tendrá únicamente dos responsabilidades:

- Identificar si el cliente accede desde un PC o una Tablet.
- Redirigir las peticiones HTTP/REST al controlador correspondiente según la solicitud realizada.

De esta manera, la identificación de dispositivos se realiza en un único componente, evitando que los controladores de noticias, suscripciones y pagos tengan que encargarse de esta comprobación.

La decisión no modifica el estilo arquitectónico cliente-servidor con API REST seleccionado anteriormente, sino que incorpora un componente para resolver el RF1.

### Consecuencias

**Positivas:**
- La identificación de PC y Tablet queda centralizada en un único componente.
- Los controladores del backend no tienen que realizar directamente esta comprobación.
- Se mantiene una separación clara entre la identificación de dispositivos y la lógica de negocio.

**Negativas:**
- Se añade un componente adicional a la arquitectura.
- El API Gateway introduce un paso intermedio en la comunicación entre el frontend y el backend.
- La identificación mediante `User-Agent` puede no ser correcta en determinados dispositivos.

**Neutras:**
- Se mantiene la arquitectura cliente-servidor con API REST.
- Los arquitectos junior deberán reflejar el API Gateway en el diagrama UML.

## Pros y Contras de las Opciones Consideradas

### Opción 1: API Gateway para discriminar clientes PC y Tablet

**A favor (+):**
- Permite realizar la identificación de dispositivos en un único punto de entrada.
- Evita repetir esta comprobación en los controladores del backend.
- Separa la identificación de los dispositivos de las funcionalidades principales del periódico.

**En contra (-):**
- Introduce un nuevo componente que debe mantenerse.
- Añade un paso adicional a las peticiones HTTP/REST.
- La cabecera `User-Agent` no garantiza que siempre se pueda identificar correctamente el dispositivo.

### Opción 2: Middleware común en el backend

**A favor (+):**
- También permite realizar la identificación de PC y Tablet en un único punto.
- No necesita incorporar un componente independiente entre el frontend y el backend.
- Evita repetir la lógica de identificación en los distintos controladores.

**En contra (-):**
- La identificación de dispositivos continúa realizándose dentro del proceso del backend.
- Es necesario mantener esta responsabilidad separada de la lógica de negocio.

### Opción 3: Identificación desde el frontend mediante CSS y JavaScript

**A favor (+):**
- Permite adaptar la presentación del periódico a las características de la pantalla.
- No requiere incorporar un API Gateway ni otro componente intermedio.

**En contra (-):**
- Adaptar la interfaz al tamaño de la pantalla no significa necesariamente identificar si el dispositivo es un PC o una Tablet.
- La información obtenida desde el navegador puede ser incompleta o incorrecta.
- Si el backend necesita conocer el dispositivo, habría que establecer cómo transmitirle esa información.

## Validación y Trazabilidad UML

La incorporación del API Gateway no modifica el estilo arquitectónico cliente-servidor con API REST seleccionado en la ADR-0001.3.

Los arquitectos junior, David Sticea y Elena Romera, deberán comprobar que el diagrama UML refleja correctamente la decisión adoptada.

Se deberá revisar que:

1. El paquete `PkgApiGateway` contiene el componente `ApiGateway` y la clase `DeviceDiscriminator`.
2. El API Gateway esté situado entre el frontend y el backend.
3. Las peticiones HTTP/REST pasen primero por el API Gateway y después lleguen a los controladores del backend.
4. La identificación de PC y Tablet se realice desde el API Gateway, sin repetir esta función en otros componentes.

### Notas de Discusión ASS-ASC

- **Objeción de Sergio González (ASC):** Sergio cuestionó si incorporar un API Gateway únicamente para distinguir entre PC y Tablet suponía añadir demasiada complejidad a la arquitectura.

- **Respuesta de Antonio Machuca y Enrique Aldama (ASS), junto con Sara Guillen (ASC):** Se explicó que el profesor Rafael Capilla había orientado al equipo hacia la utilización del API Gateway para separar la identificación de dispositivos del backend. Además, se confirmó que el componente tendría únicamente dos responsabilidades: identificar el dispositivo y redirigir las peticiones HTTP/REST.

- **Resolución ASS:** Tras valorar el cuestionamiento los senior decidieron mantener la incorporación del API Gateway considerando que la separación de responsabilidades justificaba su uso siempre que no se añadieran funcionalidades innecesarias.

## Conclusión

Tras la revisión de los arquitectos cognitivos se mantiene la decisión de incorporar el API Gateway.

Gracias a esta revisión, pudimos comprobar si realmente era necesario incorporar el API Gateway y confirmar que debía limitarse a identificar los dispositivos y redirigir las peticiones.

Por tanto, no es necesario anular la decisión anterior ni modificar nuevamente el estilo arquitectónico. Se mantiene la arquitectura cliente-servidor con API REST y se incorpora el API Gateway como punto de entrada al backend.
